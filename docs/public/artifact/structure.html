公開ディレクトリの規則

Web から見えるのは public/ の中だけ。設定ファイルやビルド定義はその外に置く。

frontend/
├── Dockerfile          ← 公開されない
├── nginx.conf          ← 公開されない
└── public/             ← ここがドキュメントルート
    ├── index.html
    ├── reader.html
    ├── css/  js/  assets/

cdn/ と docs/ も同じ形。ディレクトリを見ただけで 「何が外から見えるか」が分かるので、うっかり設定ファイルを配ってしまう事故が起きない。

マウントは public/ を 1 つだけ

compose では ./frontend/public を丸ごと 1 つマウントしている。 サブディレクトリを個別にマウントすると Docker Desktop 側でマウントが外れ、 コンテナ内が空に見えることがあるため。

本番では、この public/ の中身をそのまま GCS バケットへ流し込む。 ローカルと本番で配るものが同じになり、「本番用に書き換え忘れる」事故が起きない。

gcloud storage rsync -r frontend/public/ gs://…-frontend/
gcloud storage rsync -r cdn/public/      gs://…-cdn/
gcloud storage rsync -r docs/public/     gs://…-docs/

backend

Laravel の標準構成に、本番用の Dockerfile と設定を足したもの。

backend/
├── Dockerfile          開発用。ソースは bind mount、起動時に composer install
├── Dockerfile.prod     本番用。vendor を焼き込み、nginx + php-fpm を同居
├── docker/prod/        supervisord / nginx / php.ini / entrypoint
├── nginx.conf          開発用の前段 nginx
│
├── app/
│   ├── Http/Controllers/
│   │   ├── Api/        公開 API（BookController / HealthController）
│   │   └── Admin/      管理画面（Book / BookPage / Auth）
│   ├── Http/Requests/  バリデーション。ログイン試行の制限もここ
│   ├── Http/Resources/ JSON の整形。一覧と詳細で分けてある
│   ├── Models/         Book / BookPage / User
│   └── Console/Commands/ admin:user（管理者の作成）
│
├── routes/
│   ├── api.php         /api/*
│   ├── web.php         /  （admin ホストなら管理画面へ飛ばす）
│   └── admin.php       /admin/*  web ミドルウェアで束ねる
│
├── database/
│   ├── migrations/     books / book_pages ほか
│   ├── factories/      テストデータ
│   └── seeders/data/sample-books.json  画像生成とシードで共用
│
└── tests/Feature/      Api / Admin / TrustProxies
ルートを 3 つに割った理由

api.php と admin.php はミドルウェアが違う。 管理画面はセッションと CSRF（web）が要り、API は要らない。 ファイルごと分けておくと混ざらない。

seeders/data/sample-books.json は、画像を作るスクリプトと DB シーダーの両方が読む。 同じ書誌情報を 2 箇所に持つと、いずれ食い違うため。

│   └── reader.js       めくりの状態管理

環境ごとにファイルを差し替えない

config.js は開いているページのホスト名から接続先を決める。 環境ごとにファイルを差し替える方式だと、本番用に書き換え忘れたときに 公開サイトが localhost を見に行き、しかもサーバ側は正常なので気づきにくい。 アップロードするファイルを環境で変えなければ、その事故自体が起きない。

infra

部品（modules）と、それを組み合わせる環境（environments）に分けてある。

infra/
├── bootstrap/          tfstate バケットと API 有効化。単独で apply
│   └── backend.tf      初回 apply の後に書いて migrate-state
│
├── modules/            プロジェクト固有の値を持たない部品
│   ├── registry/       Artifact Registry
│   ├── database/       Cloud SQL + Secret
│   ├── static_site/    GCS + backend bucket + Cloud CDN
│   ├── api_service/    Cloud Run + SA + IAM（api / admin で 2 回呼ぶ）
│   ├── job/            Cloud Run Jobs
│   ├── github_oidc/    GitHub Actions からの鍵なしの認証（WIF）
│   └── frontdoor/      LB + URL マップ + 証明書 + DNS
│
└── environments/
    └── prod/           modules を組み合わせる。tfvars もここ

いまは prod の 1 環境だけだが、最初から environments/prod/ に切ってある。 後から dev を足すときにディレクトリを掘り直す作業が発生しない。コストはディレクトリ 1 段だけ。

bootstrap/ を分けているのは鶏卵問題のため。state は GCS に置きたいが、 そのバケットを Terraform で作るなら、その apply の state はどこに置くのか。 bootstrap だけローカル state で apply し、あとから backend.tf を書いて移す。

└── public/books/<code>/page-01.svg …   10 冊 × 10 ページ

tools/
├── Dockerfile          php-cli + GD

    └── generate-docs-index.php    docs の一覧（本番用）
tools は常駐しない

リクエストを受けるのではなく、CLI から単発で回す処理。 compose では profiles で通常の up から外し、 docker compose run --rm tools で都度起動する。

docs/public/index.json はリポジトリに含めていない。 ローカルは nginx の autoindex でファイル一覧を組み立てるが、GCS には autoindex が無い。 CD がデプロイの直前にだけ生成してアップロードする。 コミットしてしまうと、ローカルで古い一覧が優先されて新しいページが出なくなる。

.github（CI/CD）

検査は PR の段階、デプロイは main へのマージ。変更のあったものだけ検査する。

.github/workflows/
├── ci-backend.yml      backend/ が変わった PR で：Pint → PHPUnit
├── ci-infra.yml        infra/ が変わった PR で：fmt → validate → plan
└── cd.yml              main への push で：ビルド → デプロイ → 静的ファイルの配置

CI はファイルを分け、paths で絞っている。docs だけを直した PR で、 PHPUnit や terraform plan が走らない。

CI の backend は DB サービスを立てない。phpunit.xml が SQLite のインメモリを強制しているので、 PHP があればテストは通る。APP_KEY だけは .env.example から .env を作って生成する。

CI の infra は plan を表示するだけ。apply は差分を読んでから手で行う。 plan の結果は実行ページの Summary に出るので、PR の Checks から 1 クリックで読める。

GCP への入り方は infra 側にある

workflow には鍵を置いていない。GitHub の OIDC トークンを GCP で交換して SA になりすます仕組み （Workload Identity Federation）は、infra/modules/github_oidc/ に Terraform で書いてある。 workflow に書いているのは Provider の名前と SA のメールアドレスだけで、どちらも秘密ではない。
