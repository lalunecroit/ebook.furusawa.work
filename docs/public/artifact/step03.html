6つのコンテナ

Step.02 の4つに、db と管理画面の phpmyadmin が加わった。

3306 をホストに公開しているのは、ホスト側から artisan migrate や GUI クライアントで直接繋ぐため。データは名前付きボリューム db-data に置き、作り直したいときは docker compose down -v で丸ごと捨てる。

接続情報は compose から渡す

backend:
  environment:
    DB_CONNECTION: mysql
    DB_HOST: db          ← コンテナ間はサービス名で解決
    DB_DATABASE: ebooks_local
    DB_TIMEZONE: "+09:00"

Laravel の Dotenv は immutable で、既存の環境変数を .env の値で上書きしない。そのため .env が DB_CONNECTION=sqlite のままでも、コンテナ内では compose の値が勝って MySQL に繋がる。ホストから artisan を叩くときは .env が使われるので、DB_HOST を使い分けられる。

MySQL は起動直後には繋がらない

db には mysqladmin ping のヘルスチェックを入れ、backend と phpmyadmin は condition: service_healthy で待つ。コンテナが立ち上がった瞬間と、MySQL が接続を受け付ける瞬間には差がある。

なぜスキーマだけ先に決めるのか

このステップでは API を1行も触っていない。書籍データは Step.02 のまま BookController::BOOKS にベタ書きされている。

コードの差し替えは後からいくらでもできるが、スキーマはデータが入った後に変えると移行作業が要る。論理削除をどう表すか、一意制約をどこに張るか、カラム名をどうするか — その辺りを決め切ってからモデルとシーダーまでを用意し、API の差し替えは次のステップに回した。

実際このステップでは、テーブル定義を2回作り直している（is_active の位置とタイムスタンプの既定値、そして命名規約）。まだデータが無いので migrate:fresh で済むが、運用開始後なら差分マイグレーションと移行スクリプトの話になっていた。

テーブル設計

2テーブル。books が書誌情報、book_pages が1行=1ページ。

books                              book_pages
├ id                               ├ id
├ code          (URL 上の識別子)    ├ book_id   → books.id (ON DELETE CASCADE)
├ title                            ├ page_no
├ description                      ├ img_path  (CDN ルートからの相対パス)
├ pages_count   (非正規化した件数)  ├ created_at
├ published_at                     └ updated_at
├ is_active     (生成列)
├ deleted_at    (論理削除)
├ created_at
└ updated_at

img_path に入れるのは /books/sample/page-01.svg のような相対パスだけ。ホスト名は config/cdn.php が持っているので、CDN を実サービスに移しても DB は触らずに済む。Step.02 で引いた線をそのまま持ち込んでいる。

published_at には索引を張った。「公開済みの本を新しい順に」が一覧の基本クエリになるため。book_pages の unique(book_id, page_no) は重複ページを防ぐと同時に、ページ順の取得にも効く。

論理削除と一意制約の両立

「生存行の code は一意。削除済みの code は再利用できる」を1本の制約で表す。

素直に unique('code') を張ると、一度削除した本の code が永久に使えなくなる。かといって unique(['code', 'deleted_at']) にすると、NULL 同士は別物と判定されるため生存行の重複をまったく弾けない。論理削除でよく踏む落とし穴がここにある。

// deleted_at から導出する生成列を置き、それと複合ユニークにする
$table->unsignedTinyInteger('is_active')
    ->storedAs('CASE WHEN deleted_at IS NULL THEN 1 END');

$table->unique(['code', 'is_active']);
行の状態is_activeユニーク判定
生存1(code, 1) で比較され、重複を弾く
削除済みNULLNULL を含む行は判定対象外。何件でも共存できる

「NULL を含む行はユニーク制約の対象外」という SQL の性質を逆手に取っている。値は DB が入れるのでアプリ側は何もしなくてよく、SoftDeletes をそのまま使える。生成列に書き込むと DB エラーになるので、モデルの fillable には入れない。

型は tinyint。enum('0','1') は避ける

ENUM は内部的に 1 始まりのインデックスで値を持つ。ENUM('0','1') に対する WHERE is_active = 1（数値比較）はインデックス比較になり、1番目の要素である '0' にマッチする。クォートを1つ忘れただけで静かに壊れる。サイズはどちらも 1 バイトで差が無い。

タイムスタンプの既定値

Laravel の timestamps() をそのまま使わず、DB 側にも既定値を持たせた。

$table->timestamp('created_at')->useCurrent();
$table->timestamp('updated_at')->useCurrent()->useCurrentOnUpdate();
-- 生成される DDL
`created_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
`updated_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

Eloquent 経由なら PHP 側が値を入れるので既定値は要らない。それでも付けているのは、管理画面のバッチや生 SQL で画像を差し替えたときに updated_at が動かないと、Step.02 で組んだ ?v= のキャッシュバスターが更新されないから。「画像を差し替えたら URL が変わる」という約束を、DB 側からも守らせている。

命名を規約に寄せる

最初は books_pages / books_id だった。規約に合わせると、モデル側の明示指定が3箇所消える。

// 規約から外れていると
$table->foreignId('books_id')->constrained('books');   ← 参照先テーブルの指定が必要
$this->hasMany(BookPage::class, 'books_id');           ← 外部キーの指定が必要
#[Table('books_pages')]                                ← テーブル名の指定が必要

// 規約どおり (book_pages / book_id)
$table->foreignId('book_id')->constrained();
$this->hasMany(BookPage::class);

constrained() は「カラム名から _id を落として複数形にしたテーブル」を参照先とみなす。books_id だと bookses を探しにいくので、明示指定が必須だった。

pages ではなく pages_count

総ページ数のカラムを pages にすると、リレーション名 pages() と衝突する。Eloquent はカラムを優先するので、pages() を定義しても $book->pages は int を返し続ける。例外も警告も出ないので厄介な部類のバグになる。

// カラムを pages_count にして pages を空けておく
$book->pages;         → HasMany のコレクション
$book->pages_count;   → 件数

pages_count は withCount('pages') が生成する属性名と同じ。一覧ではカラムを読み、詳細では実数を数える、と使い分けてもコードの見た目が変わらない。将来カラムを廃止して withCount() に一本化するときも呼び出し側は無修正で済む。

モデルとシーダー

#[Fillable(['code', 'title', 'description', 'pages_count', 'published_at'])]
class Book extends Model
{
    use SoftDeletes;

    public function pages(): HasMany
    {
        return $this->hasMany(BookPage::class);
    }
}

is_active は fillable に入れていない。生成列なので、書き込もうとすると DB がエラーを返す。

$book = Book::updateOrCreate(['code' => 'sample'], [...]);

foreach (range(1, 10) as $pageNo) {
    $book->pages()->updateOrCreate(
        ['page_no' => $pageNo],
        ['img_path' => sprintf('/books/sample/page-%02d.svg', $pageNo)],
    );
}

シーダーは updateOrCreate で書いてあるので、何度流しても同じ状態になる。BookController にベタ書きしていた10ページ分をそのまま DB へ移した内容で、次のステップで API がこれを読むようになる。

タイムゾーンは3箇所

日本時間に揃えるのに3箇所の設定が要った。どれか1つでも抜けるとズレる。

どこ設定効く範囲
MySQL サーバcommand: --default-time-zone=+09:00CURRENT_TIMESTAMP、サーバ既定のタイムゾーン
Laravel アプリAPP_TIMEZONE=Asia/TokyoPHP が生成する日時（now() など）
DB 接続DB_TIMEZONE=+09:00接続ごとの time_zone。timestamp 型の解釈と変換

3つ目が要るのは、timestamp 型がセッションのタイムゾーンで解釈・変換されるから。サーバ側だけ JST にしても、接続が UTC のままなら useCurrent() で入る値がズレる。config/database.php の 'timezone' => env('DB_TIMEZONE') がこれを設定している。

名前ではなくオフセットで指定する

--default-time-zone=Asia/Tokyo と書くには mysql_tzinfo_to_sql でタイムゾーンテーブルを読み込む必要があり、未読込のまま起動すると失敗する。日本は DST が無いので +09:00 で実質同義。

テストが開発DBを見ないようにする

まだテストは書いていないが、書く前に塞いでおく必要があった。

phpunit.xml には最初からインメモリ SQLite を使う指定がある。ところが compose の environment で渡した値は、コンテナ内で本物の環境変数として $_SERVER に入る。Laravel の env() は次の順に参照する。

$_SERVERcompose の environment
▶
$_ENVphpunit の <env>
▶
putenv.env

PHPUnit の <env> が書き換えるのは $_ENV と putenv まで。$_SERVER には触らないので、このまま RefreshDatabase を使うテストを書くと、開発用の ebooks_local に接続してテーブルを落とす。

<!-- $_SERVER 側も上書きする -->
<server name="APP_ENV" value="testing" force="true"/>
<server name="DB_CONNECTION" value="sqlite" force="true"/>
<server name="DB_DATABASE" value=":memory:" force="true"/>

「テストは開発 DB を壊さない」は暗黙の前提にしがちだが、compose で環境変数を注入する構成ではその前提が崩れる。テストを書き始める前に確かめておきたい。
