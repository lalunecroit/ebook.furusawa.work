API のレスポンス仕様は、この回を通して一度も変えていない。フロントエンドは1行も触っていない。Step.02 で「ベタ書きの構造を将来のテーブルに合わせておく」と決めていたので、差し替えは素直に済んだ。

$book = Book::with(['pages' => fn ($query) => $query->orderBy('page_no')])
    ->where('code', $code)
    ->first();

abort_if($book === null, 404, "Book [{$code}] not found.");
判断理由
with() で eager loadページは必ず使う。外すとページ取得で追加クエリが走る（N+1）
total_pages は実際の行数pages_count は一覧表示用の非正規化カラムで、差し替え直後にズレうる
削除済みの本は 404SoftDeletes のグローバルスコープが自動で除外する

ここから先は、動くようになったコードを Laravel の作法に寄せていく作業になる。

ルートモデルバインディング

検索と 404 をフレームワークに任せる。URL の形は変わらない。

// モデル
#[RouteKey('code')]
class Book extends Model

// ルート
Route::get('/books/{book}', [BookController::class, 'show']);

// コントローラ
public function show(Book $book): BookResource

何が名前で、何が型で決まるのか

{book} と書いたから Book が選ばれる、のではない。解決は SubstituteBindings ミドルウェアが行い、型と名前で役割が分かれている。

決めていること由来
どのモデルクラスか型宣言 Book
どの URL パラメータの値を使うか引数名 $book ↔ {book}
どのカラムで検索するか#[RouteKey('code')]、無ければ主キー id
削除済みを含めるかモデルのグローバルスコープ（->withTrashed() で変更可）

Laravel はコントローラの引数をリフレクションで読み、UrlRoutable を実装した型の引数を探す。見つかったら同名の URL パラメータの値を取り、Model::resolveRouteBinding() で検索する。無ければ ModelNotFoundException を投げ、例外ハンドラが 404 に変換する。

名前が一致しないと静かに壊れる

ルートパラメータ名と引数名がズレていると、例外も警告も出ずにバインディングが素通りする。DI コンテナが空のモデルを作って渡すため、$book->exists === false のままコードが進む。パラメータ名を変えるときは引数名も必ず合わせる。

索引が効くようにする

バインディングが発行するクエリを見たら、複合ユニークの code 側しか使えていなかった。

-- 既定 (SoftDeletes のグローバルスコープが付ける条件だけ)
select * from books where code = ? and books.deleted_at is null limit 1

deleted_at は索引に含まれていないので、行を読んでから判定することになる。

条件typekey_lenExtra
code = ? AND deleted_at IS NULLref258（code のみ）Using where
code = ? AND is_active = 1const260（端まで使用）NULL

生存行は is_active = 1 と同値なので、バインディングの検索条件に足す。

public function resolveRouteBinding($value, $field = null)
{
    /** @var Builder<static> $query */
    $query = $this->resolveRouteBindingQuery($this, $value, $field);

    return $query->where('is_active', 1)->first();
}

上書きしたのは resolveRouteBinding() だけ。->withTrashed() を付けたルートは resolveSoftDeletableRouteBinding() を通るので、削除済みが引けなくなる事故は起きない。

Step.03 で is_active を「部分ユニークを表現するための生成列」として入れたが、検索でも使えるのがこの構成の利点だった。

API Resource

JSON の組み立てをコントローラから出す。API Resource は「共通処理置き場」ではなく、モデル → JSON の変換層（MVC の View、いわゆる Presenter）。

// app/Http/Resources/BookPageResource.php
public function toArray(Request $request): array
{
    return [
        'page_no' => $this->page_no,
        'img_path' => $this->img_path,
        'updated_at' => $this->updated_at->toIso8601String(),
        'url' => $this->url(),        ← ?v= の組み立てはここ1箇所
    ];
}
// コントローラは「取ってきて渡す」だけになる
public function show(Book $book): BookResource
{
    $this->loadPages($book);

    return new BookResource($book);
}

実利は2点。?v= の組み立てが1箇所に集まることと、data ラッパーが自動で付くこと。書籍一覧 API や管理画面のプレビューでも同じ整形が必要になるので、コピーが増える前に出しておきたい。

移行の検証

リファクタの前後で両エンドポイントの JSON を保存し、差分比較して完全一致を確認した。テストも無修正で通っている。「外から見た振る舞いが変わっていない」ことを機械的に確かめられる形にしておくと、この種の作業は安心して進められる。

テストデータの生成が手組みだったので、ファクトリに移した。

// 変更前: テストクラス内の21行のヘルパ
$book = Book::create([...]);
$book->pages()->createMany([
    ['page_no' => 1, 'img_path' => '/books/sample/page-01.svg'],

状態用途

img_path は親の書籍の code から組み立てている。ファクトリの state クロージャは (属性, 親モデル) を受け取れる（Factory::getRawAttributes() が $state($carry, $parent) と呼ぶ）ため。

public function forParentBook(): static
{
    return $this->state(fn (array $attributes, ?Book $book) => [
        'img_path' => $this->imgPath($book?->code ?? 'sample', $attributes['page_no'] ?? 1),
    ]);
}
// 実際に動かすと

page 1 : /books/demo/page-01.svg
page 2 : /books/demo/page-02.svg
page 3 : /books/demo/page-03.svg

書籍一覧 API を作るときに Book::factory()->count(20)->create() と書けるので、ページネーションのテストが楽になる。

最後の1本は API ではなくスキーマの振る舞いのテスト。部分ユニークの仕掛けはアプリ側のコードに現れないので、テストで意図を残しておかないと、後からマイグレーションを触ったときに壊れても気づけない。

sqlite と MySQL を切り替える

docker compose exec backend php artisan test                        ← sqlite (:memory:)
docker compose exec backend php artisan test -c phpunit.mysql.xml   ← MySQL (ebooks_test)

環境変数では切り替わらない。PHPUnit は XML の <server> をブートストラップ時に $_SERVER へ書き込むので、プロセスの環境変数より XML が優先される。

テスト用 DB の作成を自動化

ebooks_test を手で作っていたため、環境を作り直すと失われていた。ここは2段階で形が変わっている。

最初の案: MySQL の初期化スクリプト。db/init/01-create-test-db.sql を /docker-entrypoint-initdb.d/ にマウントする方法。ただし MySQL 公式イメージはこのディレクトリをデータディレクトリが空のとき（＝初回起動時）にしか実行しない。すでにボリュームがある環境では動かず、docker compose down -v が要る。「テストを動かすために DB を作り直す」のは本末転倒なので採用をやめた。

採用した案: PHPUnit の bootstrap で作る。

<!-- phpunit.mysql.xml -->
<phpunit bootstrap="tests/bootstrap-mysql.php" ...>

<server name="DB_ROOT_USERNAME" value="root" force="true"/>
<server name="DB_ROOT_PASSWORD" value="root" force="true"/>
// tests/bootstrap-mysql.php
$pdo = new PDO(
    sprintf('mysql:host=%s;port=%s', $_SERVER['DB_HOST'], $_SERVER['DB_PORT']),
    $_SERVER['DB_ROOT_USERNAME'],
    $_SERVER['DB_ROOT_PASSWORD'],
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION],
);
$pdo->exec("CREATE DATABASE IF NOT EXISTS `{$database}` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci");
$pdo->exec("GRANT ALL PRIVILEGES ON `{$database}`.* TO '{$username}'@'%'");

require __DIR__.'/../vendor/autoload.php';

PHPUnit は bootstrap に指定したファイルをテスト実行のたびに最初に読み込む。そこで DB を用意してから vendor/autoload.php を読ませる形にした。

利点内容
いつ実行しても効くボリュームの状態に依存しない。既存環境でもそのまま動く
CI でも同じ手順service container 側の初期化スクリプトに頼らなくてよい
冪等CREATE DATABASE IF NOT EXISTS と GRANT は何度流しても同じ結果

root の資格情報を使うのは、MYSQL_USER で作られる ebooks が MYSQL_DATABASE（＝ebooks_local）の権限しか持たず、新しい DB を作れないため。sqlite 版はインメモリなのでこの準備は要らない。

php-fpm + nginx へ

artisan serve は PHP のビルトインウェブサーバ（php -S）を起動するラッパーで、開発用。シングルプロセスで同時リクエストを捌けない。

ブラウザ:8000
▶
backend-webnginx。静的ファイルを返す
▶
backendphp-fpm :9000。PHP の実行のみ
root /app/public;                                   ← 公開は public/ だけ

location / { try_files $uri $uri/ /index.php?$query_string; }

location ~ \.php$ {
    fastcgi_pass backend:9000;
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
}

両コンテナで ./backend を /app にマウントしているのがポイント。SCRIPT_FILENAME は nginx が組み立てたパスを php-fpm が開くため、パスが一致していなければ動かない。

clear_env の罠

症状は artisan serve のときと同じ

php-fpm の既定は clear_env = yes で、ワーカー起動時に環境変数をすべて捨てる。compose の DB_HOST=db が届かず Connection refused になる。原因の仕組みは違うのに症状が同じ、という厄介な組み合わせ。

; backend/php-fpm.d/zz-app.conf
[www]
clear_env = no

php-fpm.conf は include=/usr/local/etc/php-fpm.d/*.conf で読み込み、ファイル名順に後勝ちで上書きする。zz- で始めているのは既定値の www.conf より後に読ませるためで、公式イメージ自身も zz-docker.conf という名前を使っている。

これに伴い、Step.04 の途中まで必要だった ServeCommand::$passthroughVariables への追加は削除できた。serve を使わなくなったので迂回が要らない。

公開範囲

ドキュメントルートが public/ に限定されるため、ソースや設定は配信されない。

ハマりどころと積み残し

症状原因
Connection refused（HTTP だけ）artisan serve が子プロセスに環境変数を渡さない。php-fpm では clear_env = yes が同じ症状を起こす
バインディングが効かず空のモデルが渡るルートパラメータ名と引数名の不一致。例外は出ない
索引が部分的にしか効かないdeleted_at IS NULL は複合ユニークに含まれない。is_active = 1 を使う
テストの接続先が切り替わらないPHPUnit の XML が $_SERVER を上書きする
MySQL の初期化 SQL が実行されない/docker-entrypoint-initdb.d/ はデータディレクトリが空のときだけ動く。既存環境には効かないので、テスト用 DB は bootstrap で作る
ブランチ切り替え後に 403 / 404Docker Desktop のバインドマウントが外れている。--force-recreate で作り直す

積み残し

  • フロントと API がオリジンで分かれている。reader.js に http://localhost:8000 が直書きされたままで、CORS も必要。backend-web に frontend の配信を寄せるか、frontend 側に /api のプロキシを足せば、どちらも不要になる
  • 書籍一覧 API が無い。pages_count はそのための非正規化カラムだが、まだ使い道がない
  • 認証（users テーブルは雛形のまま残してある）
