PR のブランチからデプロイ権限を使えると、レビュー前のコードを本番に出せてしまう。

信頼の条件は 3 段

① Provider：このリポジトリ以外は交換させない

attribute_condition = "assertion.repository_id == '1378122529'"

名前ではなく数値 ID。リポジトリを消して作り直すと、他人が同じ名前を取れるため。

② deployer：subject が main への push と一致したときだけ

repo:lalunecroit@38752755/ebook.furusawa.work@1378122529:ref:refs/heads/main

ref ではなく subject で縛る。pull_request_target は PR 起点なのに ref が main になるが、subject は …:pull_request なので一致しない。

③ planner：リポジトリが一致すれば全ブランチ

読み取り専用なので広くてよい。フォークからの PR には GitHub が OIDC トークンを発行しないので、外部の人は使えない。

subject の形式はリポジトリで違う

このリポジトリは「不変 ID 付き」（use_immutable_subject: true）で、名前の後ろに数値 ID が付く。名前だけの形式（repo:owner/name:…）で縛ると一致せず、なりすましが 403 になる。形式は gh api repos/<owner>/<name>/actions/oidc/customization/sub で確認できる。

権限を触るものにだけ付ける

roles/editor を渡せば楽だが、漏れたときに何でもできてしまう。

SA役割対象
deployerartifactregistry.writerリポジトリ app だけ
run.developerapi / admin / migrate だけ
iam.serviceAccountUser上の 3 つの実行時 SA だけ（actAs）
storage.objectAdmin + legacyBucketReaderfrontend / docs だけ（cdn は除外）
カスタムロールCDN のキャッシュ無効化だけ
plannerviewer + iam.securityReviewerプロジェクト全体（読み取り）
storage.objectViewertfstate バケット
secretmanager.secretAccessorDB パスワードだけ

actAs。Cloud Run の新しいリビジョンは実行時の SA として動く。デプロイする側がその SA への actAs を持っていないと、差し替え自体が権限エラーになる。

カスタムロール。既成の役割だと compute.loadBalancerAdmin まで上げる必要があり、LB の設定を書き換えられてしまう。無効化に要る 3 権限だけにした。

cdn を外す。本番の画像は管理画面から入るもので、リポジトリの cdn/public/ はサンプル。毎回 rsync すると本番のデータと混ざる。

planner は DB パスワードを読める

state には DB パスワードが平文で入っていて、planner は state を読む。このリポジトリに push できる人は、間接的に DB パスワードを読めることになる。個人のリポジトリなので許容している。

タグはコミットハッシュ

どのコミットが本番で動いているか一目で分かり、戻すときもタグを差し替えるだけ。Step.08 の未決事項「v1 固定かコミットハッシュか」はここで決着した。

マイグレーションは先に

新しいコードが新しいテーブル定義を前提にしていても、切り替えた瞬間に壊れない。ただし列を消す変更は、古いコードが動いている間に壊れるので段階を分ける。

Docker の認証はトークンを直接渡す

- id: auth
  uses: google-github-actions/auth@v3
  with:
    token_format: access_token
- uses: docker/login-action@v4
  with:
    username: oauth2accesstoken
    password: ${{ steps.auth.outputs.access_token }}

補助コマンド（gcloud auth configure-docker）を経由しない。auth アクションの公式の推奨。

CDN の無効化は www と docs だけ

cdn. の画像は ?v= で URL が変わる仕組みなので消す必要がない。消すと全画像がオリジンから取り直しになる。

ランナーは amd64 なので、手元の Apple Silicon で要った --platform linux/amd64 は不要。Docker のレイヤは GitHub 側にキャッシュする。

インフラの変更を含むとき

develop にマージしたあと、main にマージする前に terraform apply。CD は GCP の権限を前提に動くので、先に main に入れると権限の変更が間に合わずに落ちる。

ハマりどころ

CD は main でしか動かないので、本番へのリリースそのものが初回の実行になる。そこで出たものを並べる。

症状原因
push で error getting credentials（本文が空）subject が一致せず SA になりすませていない。資格情報ファイルを書くだけの auth ステップは成功に見え、Docker の補助コマンドが交換する段階で本文の無いエラーになる
auth で getAccessToken が 403同上。subject を名前だけの形式で縛っていたが、このリポジトリは不変 ID 付きの形式
rsync で storage.buckets.get が 403objectAdmin はバケットのメタデータを読めない。legacyBucketReader を足す
plan に毎回 client = "gcloud" -> nullgcloud でデプロイすると付く印。ignore_changes に入れる
手元から planner になりすませないOwner でも getAccessToken は含まれない。IAM を書き換えてまで試さず、CI で確かめる
