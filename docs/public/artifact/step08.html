鶏卵問題の解き方

state は GCS に置きたい。でもそのバケットを Terraform で作るなら、その apply の state はどこに置くのか。

bootstrap
local state
→
GCS バケット
が出来る
→
backend.tf
を書く
→
-migrate-state
state が移る

bootstrap に入れるのは 2 つだけ。

  • tfstate 用の GCS バケット — バージョニング必須。state の破損や誤 apply からの復旧手段がこれしかない
  • google_project_service — 上の表の「未有効」7 つ

API 有効化を bootstrap 側に置くのには理由がある。terraform apply の直後は有効化が伝播しておらず、続けて作るリソースが API has not been used… で落ちることがある。先に bootstrap を流しておけば、この揺れを踏まない。

書く順番

apply が 2 回に分かれる。イメージが存在しないと作れないリソースがあるため。

# ① 土台（ローカル state → GCS へ移行）
cd infra/bootstrap
terraform init && terraform apply
terraform init -migrate-state   # backend.tf を書いてから

# ② 本体（イメージが要るリソースの手前まで）
cd ../environments/prod
terraform apply -target=module.registry

# ③ イメージを push
docker build -f backend/Dockerfile.prod -t <registry>/app/api:v1 ./backend
docker push <registry>/app/api:v1

# ④ 残り全部
terraform apply

# ⑤ 静的ファイルを流し込む
# ⑥ ネームサーバをレジストラ側に設定

ディレクトリは最初から environments/prod/ に切る。いまは 1 環境だけだが、後から dev を足すときに掘り直す作業が発生しない。コストはディレクトリ 1 段だけ。

Terraform 以外の積み残し

設計を読み直して見つかった、コード以外に必要なもの。

マイグレーションと管理者ユーザ

コンテナ起動時には流さない（Step.07 の 10）。Cloud Run Jobs か手動で流す。

gcloud run jobs create ebook-migrate --image <IMAGE> \
  --command php --args artisan,migrate,--force
gcloud run jobs execute ebook-migrate

artisan admin:user も同じ経路で流す。

Secret Manager への値の投入

値を Terraform で作ると tfstate に平文が残る

シークレットの「箱」だけ Terraform で管理し、値は gcloud secrets versions add で手投入する。tfstate バケットのアクセス権を絞るだけでは、state を読める全員に見えてしまう。

ドメインまわりで必要な作業

furusawa.work は Cloud DNS 上にあり、そのゾーンは今回のプロジェクトに属している。レジストラ（お名前.com）の NS も ns-cloud-a1〜a4.googledomains.com を向いているため、レジストラで行う作業は無い。ゾーン furusawa-work の中身は NS と SOA だけで、ebook.furusawa.work は未設定。

このステップで行うのは ebook. 配下の A レコードを既存ゾーンに追加することだけ。専用ゾーンは作らない。親ゾーンが空なので隔離の利点が無く、委任を挟まない分だけ証明書の発行も速い。

// 手で作られた既存ゾーンを、作らずに参照する（import は不要）
data "google_dns_managed_zone" "root" {
  name = "furusawa-work"
}

resource "google_dns_record_set" "api" {
  managed_zone = data.google_dns_managed_zone.root.name
  name         = "api.ebook.${data.google_dns_managed_zone.root.dns_name}"
  type         = "A"
  ttl          = 300
  rrdatas      = [google_compute_global_address.lb.address]
}
効いてくるところ

親ゾーンが Terraform の管理外であることは安全側に働く。terraform destroy してもゾーン自体は残り、ドメインが死なない。実施のタイミングは LB 一式と同じ段。A レコードの中身が LB の静的 IP なので、IP を確保するまで書けない。
