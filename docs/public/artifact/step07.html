本番用イメージを作る

開発用の Dockerfile は bind mount 前提で、起動のたびに composer install が走る。本番用は別ファイルに分けた。(1 / 2 / 3)

Cloud Run は1コンテナしか起動できない。開発では nginx と php-fpm を別サービスに分けていたが、本番は supervisord で同居させる。

層開発本番
HTTPbackend-web コンテナ同一コンテナ内の nginx
PHPbackend コンテナ同一コンテナ内の php-fpm
接続fastcgi_pass backend:9000fastcgi_pass 127.0.0.1:9000
vendorホストを bind mountビルド時に焼き込む
ポート80 固定$PORT（既定 8080）

ここで一番効いたのは 片方のプロセスが死んだときの扱いだった。php-fpm だけ落ちて nginx が生き残ると、コンテナは「起動中」に見えるのに全リクエストが 502 になる。supervisord のイベントリスナで、どちらかが終了したらコンテナごと落とすようにした。

; supervisord.conf — 片肺運転をさせない
[eventlistener:quit_on_failure]
command=/usr/local/bin/stop-supervisor.sh
events=PROCESS_STATE_FATAL,PROCESS_STATE_EXITED

実際に kill -9 で php-fpm を落として確認した。イベントリスナが発火し、nginx も停止してコンテナが終了する。Cloud Run ならここで新しいインスタンスが作り直される。

ビルド初回は起動に失敗した

Class "Laravel\Pail\PailServiceProvider" not found。bootstrap/cache/packages.php は git 管理外だが、.dockerignore は .gitignore とは別物なので、開発中に生成された「dev 依存を含む検出キャッシュ」がイメージに入り込んでいた。--no-dev の vendor には laravel/pail が無いので落ちる。

黙って壊れる設定を起動時に止める

このステップで一番学びがあった部分。設定を忘れてもコンテナは起動し、API は 200 を返す。壊れているのは利用者から見える一部分だけで、監視には映らない。(5 / 6)

設定忘れると気づくのは
APP_KEY起動する。DB を読む API も 200管理画面にログインしようとした瞬間
MissingAppKeyException
CDN_BASE_URL起動する。API も 200画像URLが http://localhost:8082/… になり、ブラウザで全ページの画像が出ない

どちらも「既定値のままだと間違っている」種類の設定なので、entrypoint で先に止めることにした。

# 未設定なら起動を中止する
if [ -z "${APP_KEY}" ]; then
  echo "[entrypoint] APP_KEY が設定されていません。起動を中止します。" >&2
  exit 1
fi

# base64: 形式なら鍵長も見る。短い鍵は起動を通過して暗号化の時点で落ちる
case "${APP_KEY}" in
  base64:*)
    key_bytes=$(printf '%s' "${APP_KEY#base64:}" | base64 -d | wc -c)
    [ "${key_bytes}" = 32 ] || [ "${key_bytes}" = 16 ] || exit 1
    ;;
esac
守りを入れる基準

全部の環境変数を必須にはしていない。「既定値のままだと間違っている」ものだけを止める。SESSION_DRIVER は既定値がそもそも正しい（database）ので入れていないし、APP_URL は間違っていても現状は壊れないので入れていない。

接続と URL の前提

3 項目。うち 2 つはコードを書かずに終わった。実機で測って「不要だった」と分かった形。(4 / 8 / 9)

Cloud SQL への UNIX ソケット接続 (4)

config/database.php には最初から 'unix_socket' => env('DB_SOCKET', '') があり、変更は要らなかった。設計メモには「TCP 用の DB_HOST は空にする」と書いてあったが、実測したら空にする必要はなかった。

条件結果
DB_SOCKET のみ接続成功
DB_SOCKET + DB_HOST=存在しないホスト接続成功
DB_SOCKET 空 + 存在しないホスト（対照）getaddrinfo で失敗

MySqlConnector::getDsn() は unix_socket が空でなければ host/port を一切見ない。3 番目の対照実験が失敗したことで、テスト自体が機能していることも確認できた。

db:show の Host 欄は当てにならない

ソケット接続でも config('database.connections.mysql.host') の値をそのまま表示する。上の 2 番目では this-host-does-not-exist と表示されながら、実際にはソケットで繋がっていた。

APP_URL はリクエスト中には効かない (8)

APP_URL とリクエスト元をわざと食い違わせて測った。

# APP_URL = https://api.ebook.furusawa.work / リクエストは http://localhost:9098
Web リクエスト中の route()  → http://localhost:9098/admin/login   ← リクエスト由来
コンソールの route()        → https://api.ebook.furusawa.work/…   ← APP_URL 由来

効くのは artisan・キュー・メールのようにリクエストが無い文脈だけ。このアプリはそのどれも使っていないので、現状 APP_URL は実行時の挙動に影響しない。それでも値を入れるのは、後でキューを足したときに http://localhost が混入しないようにするため。

TrustProxies は Proto と Port だけ信頼する (9)

LB が TLS を終端するので、転送ヘッダを信頼しないと生成 URL が http:// のままになる。ただし X-Forwarded-For はあえて信頼しない。

$middleware->trustProxies(
    at: '*',
    headers: Request::HEADER_X_FORWARDED_PROTO | Request::HEADER_X_FORWARDED_PORT,
);

ログインのレート制限が email|ip をキーにしているため、信頼するとクライアントが IP を名乗り換えるだけで総当たり対策を回避できる。さらに Google の LB は受け取った X-Forwarded-For の右側に実 IP を足す形式なので、左端を実 IP とみなす Symfony の既定とは噛み合わない。信頼しなければ $request->ip() はプロキシの IP になるが、これは変更前と同じ挙動なので退行しない。

届く範囲を絞る

サブドメインで役割を分けた結果、誰がどこに届いてよいかを明示する必要が出てきた。(7 / 15 / 16)

CORS (7)

config/cors.php を置いていなかったので、フレームワーク既定の allowed_origins => ['*'] が効いていた。どのサイトからでも API を読める状態だった。

// 環境ごとに変わるのでカンマ区切りの環境変数から読む
'allowed_origins' => array_values(array_filter(array_map(
    trim(...),
    explode(',', (string) env('CORS_ALLOWED_ORIGINS', 'http://localhost:8080')),
), static fn (string $origin): bool => $origin !== ''))
許可オリジンが1つだと挙動が変わる

開発で https://evil.example から叩いても Access-Control-Allow-Origin: http://localhost:8080 が返ってきて、一瞬バグに見えた。php-cors は許可が 1 つだけならリクエスト元に関係なく固定値を返す（isSingleOriginAllowed）。値が一致しないのでブラウザが弾く＝安全側だが、「許可外ならヘッダが無い」と思い込むと読み違える。テストに明示して残した。

セッション Cookie (15)

設計メモは SESSION_DOMAIN=admin.ebook.furusawa.work を入れる想定だったが、実測すると逆だった。

未設定 → Set-Cookie: …; path=/; httponly; samesite=lax
指定   → Set-Cookie: …; path=/; domain=admin.ebook.furusawa.work; httponly; samesite=lax

RFC 6265 では Domain を省くとホスト限定 Cookie になり、そのホストにしか送られない。指定すると配下のサブドメインにも送られる。つまり null の方が厳しいので、そちらを採用した。

SESSION_SECURE_COOKIE は環境変数で渡すのをやめ、既定値を APP_ENV=production なら true にした。渡し忘れても安全側に倒れる。

管理画面のホスト限定 (16)

api. と admin. は同じイメージの別サービスなので、そのままだと api.ebook.furusawa.work/admin/… でも管理画面に届く。

ADMIN_HOSTHost ヘッダ/admin/login/api/books
admin.ebook.…admin.ebook.…200200
api.ebook.…404200
www.ebook.…404200
未設定どれでも200200

空なら制限しない作りにしてある。開発は api も admin も localhost で兼ねているため。公開 API は www. から叩かれるのでホスト制限をかけていない。

使い捨てインスタンスの前提

Cloud Run のインスタンスは使い捨てで、同時に複数立つ。ローカルの前提がそのまま壊れる。(10 / 13 / 14)

セッションがファイルだと切れる (13)

同じ DB を共有する 2 インスタンスを立て、A でログインして同じ Cookie で B を叩いた。

SESSION_DRIVER同じインスタンス(A)別インスタンス(B)
file200302（ログイン画面へ）
database200200

調べると本番イメージは既に database だった。.dockerignore で .env を除外しているため config/session.php の既定値が効く。実際の問題は「開発が file、本番が database」という食い違いで、この状態ではセッション絡みの不具合がローカルで再現しない。

マイグレーションは起動時に流さない (10)

起動時に流さないことは最初から満たしていた。足りなかったのは分離した実行経路のほうで、同じイメージに artisan を渡すと Web 用の準備が全部走り、画像URLを作らない migrate にまで CDN_BASE_URL を要求して失敗していた。

# entrypoint に実行モードの分岐を入れる
case "${1:-}" in
  supervisord) run_mode=web ;;
  *)           run_mode=oneshot ;;
esac

oneshot では nginx 設定生成もキャッシュ作成も飛ばし、要求するのは APP_KEY だけにした。Cloud Run Jobs から php artisan migrate --force を叩ける。

画像の保存先を GCS にする (14)

設計メモのとおり disk の定義だけの差し替えで済み、Storage::disk('cdn') を呼ぶコントローラは 1 行も変えていない。ただし書かれていない前提が 2 つあった。

そのままでは動かない2点

(a) Laravel が同梱するドライバは local / s3 / ftp / sftp だけで gcs は無い。Storage::extend で自分で繋ぐ必要がある。
(b) 'visibility' => 'public' をそのまま渡すと 400 になる。allUsers:objectViewer をバケットに付ける形は均一なバケットレベルのアクセスで、オブジェクト単位の ACL が使えない。UniformBucketLevelAccessVisibility を渡して無効化する。

検証は fake-gcs-server に向けて実施した。put / exists / get / size / delete と、管理画面が実際に使う putFileAs まで通ることを確認している。

フロントの接続先 (12)

ベースURLは reader.js と library.js に同じ値が重複していた。js/config.js に集約し、開いているページのホスト名から接続先を決める方式にした。

環境ごとにファイルを差し替える方式にしなかったのは、本番用に書き換え忘れると公開サイトが localhost の API を見に行くため。§02 と同じ種類の事故で、アップロードするファイルを環境で変えなければ起きない。

アップロード上限は4層ある

「32MiB 未満に揃える」の 揃える対象が 4 つあった。外側ほど大きくないと内側まで届かない。(17)

層値役割
Laravel バリデーション8MB利用者に見える上限。日本語のエラーを出す
upload_max_filesize10Mここが 8MB 未満だと PHP がファイルを捨てる
post_max_size12Mファイル + フォーム項目 + マルチパート境界
client_max_body_size16mnginx
Cloud Run32MiB変更不可。上のすべてが下回ること

開発の PHP が既定の 2M / 8M のままで、アプリが許すはずの 5.61MB が弾かれていた。しかも出るのは日本語メッセージですらない。

# 5.61MB を送った結果（アプリの上限は 8MB）
画像 failed to upload.

本番だけ 30M にしていたため、ローカルでは再現しない状態になっていた。php.d/zz-app.ini を追加して揃えた結果が次のとおり。

 5MB  → HTTP 201  成功
 9MB  → HTTP 302  「画像は 8MB 以内にしてください。」
20MB  → HTTP 413  nginx が受け取り拒否

Terraform を書く前の準備

Terraform で作れないもの＝ Terraform を動かすための土台。ここだけは手で叩く。

項目結果
terraformv1.16.3
GCP プロジェクト作成済み・課金紐付け済み
認証（ADC）application_default_credentials.json + quota project
権限roles/owner
brew install terraform は通らない

2023 年に HashiCorp がライセンスを BUSL へ変更し、homebrew-core から外された。No available formula with the name "terraform" が出る。公式 tap（brew tap hashicorp/tap）か OpenTofu を使う。

API の有効化（google_project_service）は Terraform 側でやる。bootstrap が使う storage.googleapis.com と serviceusage.googleapis.com は既に有効だったので、鶏卵問題は踏まずに済む見込み。

ハマりどころ

実機で動かすまで分からなかったもの。

  • nginx の access_log off が効かない。 ヘルスチェックをログから外そうと location = /api/health に書いたが、try_files で /index.php へ内部リダイレクトされ、ログは最終的に処理した location ~ \.php$ の設定で出る。map による条件付き access_log に変更した。
  • nginx.conf はバインドマウントでも reload が要る。 ファイルは即座に反映されるが、プロセスは古い設定で動き続ける。20MB のテストで 413 のはずが 200 を返して気づいた。
  • .dockerignore は .gitignore とは別物。 git 管理外のファイルでもビルドコンテキストには入る。dev 依存を含む検出キャッシュが本番イメージに混入した。
  • ルートのホスト制限はアプリ起動時に確定する。 テストで config() を後から書き換えても効かず、createApplication() を上書きする必要があった。
  • PNG は中身次第で圧縮される。 大きいファイルを作るテストで、規則的なピクセルだと 5MB のつもりが 0.0MB になった。os.urandom で非圧縮データにして作り直した。
まとめ

17 項目のうち、実際に設計メモと違っていたのは 4 つ（4 の DB_HOST、15 の SESSION_DOMAIN、14 の visibility、17 の層の数）。どれも「書かれていることが間違い」ではなく、実機で測らないと分からない粒度の話だった。
