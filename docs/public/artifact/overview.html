サービスの姿

本を「読む」側と「登録する」側の 2 つを、別のサブドメインで提供している。

URL役割機能
ebook.furusawa.work電子書籍サイト書籍一覧、ビューア（ページめくり）
admin.ebook.furusawa.work管理画面書籍の登録・編集、ページ画像のアップロード

ビューアは 画像 2 枚だけを重ねて ページをめくる。総ページ数が増えても DOM は増えない。 綴じ目を軸に rotateY させ、backface-visibility: hidden で 90 度を超えた紙が自動的に消えるので、 「いつ紙を隠すか」を JS で判定する必要がない。

管理画面は Blade で backend の中に閉じ込めた。フォーム送信・CSRF・バリデーションの差し戻しを Laravel に任せられる。画像は 1 枚ずつドラッグ&ドロップでアップロードする。

同じコード、違う顔

公開 API と管理画面は 1 つの Laravel アプリで、本番では同じコンテナイメージを 2 つの Cloud Run サービスとして動かしている。違うのは環境変数と 権限 だけ。

ホストから見た GCP リソース相関

6 つのホスト名は すべて同じ IP・同じ LB・同じ証明書 を指す。 振り分けているのは URL マップの host_rule だけで、増えているのは DNS レコードと証明書のドメイン名に過ぎない。

分けてもコストは増えない

サブドメインを 5 つに割っても、IP も転送ルールも証明書も 1 つのまま。 ホスト名の振り分けは URL マップの中で完結する。増えるのは DNS レコードだけで、これはゾーン料金に含まれる。

画像は API を経由しない。API が返すのは URL だけで、ブラウザはそれを <img src> に入れて CDN から直接読む。PHP を画像の通り道にしないことで、 API は JSON を返すだけの軽い処理に保てる。

本を登録する

▶

▶

アップロード後に touch() で updated_at を進める。API が返す URL の ?v= が変わるので、Cloud CDN に古い画像が載っていても新しい URL として取りに行く。 キャッシュの手動無効化が要らない。

ホストを跨がせない

api と admin は同じイメージなので、api.ebook…/admin/login にもルートは存在する。 ADMIN_HOST と Route::domain() でホストを縛り、届かないようにしてある。 LB の振り分けとアプリ側の 2 枚で塞いでいる。

Cloud SQL の IP

パブリック IP は持たせている。Cloud Run の Unix ソケット接続は内部で Cloud SQL Auth Proxy が動き、 実データは IP に対して流れるため、消すと Cloud Run 自身が繋がらなくなる（VPC が要る）。

危険なのは IP を持つことではなく 許可リストを開けること。空にしてあるので、 パスワードを知っていても素の mysql -h は通らない。接続できるのはプロキシ経由だけで、 それには IAM の cloudsql.client が要る。認証をネットワーク層ではなく IAM に寄せている。

ローカル環境

docker compose up -d で 8 サービスが立ち上がる。本番との対応を保ったまま、置き換えられる部分だけ置き換えてある。

本番 DB を手元から覗く

docker compose --profile prod-db up -d で Cloud SQL Auth Proxy と 本番用 phpMyAdmin（:8084）が立つ。本番側だけ自動ログインを外してある。 見た目の似た phpMyAdmin が 2 つ並ぶので、パスワードを取りに行く一手間を 「いま本番を触っている」という確認に使う。

設計で効いた判断

あとから効いてきたもの、踏んで学んだものを 6 つ。

api と admin を分けた理由は権限

処理の重さではない。管理画面は cdn バケットへ書き込むが、公開 API は読みすらしない （画像はブラウザが CDN から直接読む）。同じサービスに載せると、公開 API 側の穴から 書き込み権限まで届く。サービスを分ければ SA が別になり、公開 API に storage.objectAdmin を一切与えずに済む。

論理削除と一意制約を両立させる生成列

削除済みの本と同じ code を再登録したい。しかし現役の本は重複させたくない。 NULL を含む行は unique の判定対象外になる性質を使い、生成列を足した。

-- deleted_at が NULL のときだけ 1、それ以外は NULL
is_active tinyint GENERATED ALWAYS AS
  (case when deleted_at is null then 1 end) STORED
UNIQUE KEY (code, is_active)

MySQL 8.0 でも同じ DDL がそのまま通ることを実機で確認した。

キャッシュは長く持たせ、URL を変える

ページ画像は max-age=31536000, immutable で配る。差し替えたら touch() で updated_at を進め、API が返す ?v= を変える。 キャッシュを消しに行くのではなく、別の URL にする。

シークレットは種類ごとに扱いを変える

Terraform の state は平文。Terraform が値を使うかどうかで分けた。

APP_KEY は Cloud Run が参照するだけなので、箱だけ作って値は手投入。state に残らない。 DB パスワードは google_sql_user を作るのに必要なので生成まで任せ、代わりに tfstate バケットを非公開・バージョニング・public_access_prevention で固めた。

段階を分けて apply する

「課金が始まる地点」と「待ち時間が出る地点」で区切った。区切りは -target ではなく コードを書く順番で作る。その段のモジュールを書いた時点で apply すれば、 まだ書いていないものは作られない。

A registry  → イメージが要るリソースの手前
B database  → 約 1,800 円/月 が発生
C GCS + Cloud Run
D LB + 証明書 + DNS  → 約 2,900 円/月、証明書待ち 15〜60 分

本番で踏んだ落とし穴

Apple Silicon で --platform linux/amd64 を忘れる。 push も deploy も成功したように見えて、起動時に exec format error で落ちる。

edition を省略した。MYSQL_8_4 を指定したら API が ENTERPRISE_PLUS を選び、db-f1-micro（614 MiB）が弾かれた。 そちらの最小は 16 GiB で月額が一桁変わる。既定値が他の引数に応じて変わる引数は省略しない。

本番イメージに Faker が無い。db:seed が Call to undefined function fake() で落ちた。dev 依存なので --no-dev では入らない。 そもそも雛形の Test User を本番に作るべきではないので、環境で囲った。

Terraform の組み立て

infra/
├── bootstrap/            tfstate バケットと API 有効化。単独で apply
├── modules/
│   ├── registry/         Artifact Registry
│   ├── database/         Cloud SQL + Secret
│   ├── static_site/      GCS + backend bucket + Cloud CDN
│   ├── api_service/      Cloud Run + SA + IAM（api / admin で 2 回呼ぶ）
│   ├── job/              Cloud Run Jobs
│   ├── github_oidc/      GitHub Actions からの鍵なしの認証（WIF）
│   └── frontdoor/        LB + URL マップ + 証明書 + DNS
└── environments/prod/    上記を組み合わせる

鶏卵問題。state は GCS に置きたいが、そのバケットを Terraform で作るなら その apply の state はどこに置くのか。bootstrap/ だけローカル state で apply し、 あとから backend.tf を書いて terraform init -migrate-state で移した。

DNS ゾーンは Terraform の管理外。data で参照するだけにしてある。 terraform destroy してもゾーンは残り、ドメインが死なない。

イメージの更新は Terraform の仕事にしない。ignore_changes を付けてあり、 main へのマージで CD（§07）が差し替える。インフラの変更だけは、plan を読んでから手で apply する。

SA を CD 用と CI 用に分ける

デプロイ権限（github-deployer）は main への push からだけ使える。 PR のブランチから使えると、レビュー前のコードを本番に出せてしまう。 plan 用（github-planner）は読み取り専用なので、全ブランチから使える。

信頼の条件は数値 ID で縛る

このリポジトリ以外からのトークンは交換させない。名前ではなく数値 ID で判定するので、 リポジトリが消されて同じ名前で作り直されても一致しない。 GitHub が出す subject も owner@id/name@id の不変 ID 形式に合わせてある。

権限は触るものにだけ

roles/editor は渡さない。デプロイ用 SA が書けるのは frontend と docs のバケットだけで、 cdn は除外（本番の画像は管理画面から入るもので、サンプルで上書きしない）。 CDN の無効化は、無効化に要る 3 権限だけのカスタムロールにした。

インフラは自動で apply しない

CI は terraform plan を表示するだけで、apply は差分を読んだうえで手で行う。 インフラの変更を含むときは、main にマージする前に apply する。CD は GCP の権限を前提に動くので、 先に main に入れると権限の変更が間に合わずに落ちる。
